# F3 — Agent messaging end to end in sandboxes

Task: `steady-harbor-87.4`. Plan: commit `962ad38` (`docs/superpowers/plans/2026-11-04-F3-agent-messaging.md`). Implementation and evidence: one squashed commit, the one containing this document. The exact published OID is recorded in the AQ task close.

## Decisions

- **Delivery mode is a runner input.** No profile field names a delivery mode, so the caller passes `Delivery::Inbox` or `Delivery::Native(&mut dyn SafeBoundary)`. Harnesses without a qualified safe-boundary adapter (Codex today) use the inbox.
- **The safe boundary takes two steps.** The plan had a single `inject` returning `Handed | Deferred | Unknown`. It is now `ready()` followed by `inject() -> Handed | Unknown`. A boundary that is not ready therefore never records an injection intent, and a later replay cannot misread an earlier deferral as `delivery_unknown`.
- **Supervisor mail is pinned locally.** Vendored aq-agent-api 0.1.0 has only task/session recipients and owner/session senders. `aq_agent_client::mail` pins two additive `oneOf` branches, both with exact keys and non-nil UUIDs:
  - recipient `{"kind":"global_supervisor","conversation_id"}`;
  - sender `{"kind":"central_supervisor","actor_id","generation","session_id","conversation_id"}`.

  Every other part of a document is still checked by the vendored schema. The server and contract side is a CROSS-REPO FOLLOW-UP (aq-server), posted on the task.
- **Owner senders get no reply.** Agent-access v1 has no owner mailbox, so a reply to an owner sender is refused before anything is sent.

## Delivered

### Runner mail loop (`crates/aq-worker/src/native/runner/sandbox/mail.rs`)

- **API:**
  - `MailLoop::open(RunnerHttp, journal_dir)` takes its identity and attempt from `launch_binding().session` (`SessionIdentity::Remote`).
  - `poll_once(AttemptInput, Delivery) -> Vec<(delivery_id, disposition)>`.
  - `record_intent(delivery_id, message_id, digest)`.
- **Transport:** `/v2/worker/messages/poll` and `/ack` go only through the permit-bound `RunnerHttp::post_bounded`, so `check_body` binds node, boot, attempt and session. Bounds:

  | Request | Request max | Response max |
  | --- | --- | --- |
  | Poll | 4 KiB | 1 MiB |
  | Ack | 4 KiB | 16 KiB |

  Polls ask for at most 16 envelopes.
- **Batch checks.** Each batch must:
  - validate against `MessageNodeBatch`;
  - echo the request attempt;
  - hold at most 16 deliveries;
  - not repeat a `delivery_id`.

  Every receipt is journaled, or matched against its journal entry, before any effect in the batch. A replay with a different `message_id` or `payload_digest` fails the whole pass with nothing delivered.
- **Journal.** Each stage is one create-new durable file (`aq_session_host::durable_new`), in this order:
  - `received`;
  - `receipt-acked`, only for deferrals;
  - `intent`;
  - `outcome`, which holds `{disposition, ack_op}`;
  - `acked`.
- **Decision for a delivery with no outcome yet:**
  1. An intent exists: `delivery_unknown`, which is never retried.
  2. Else the attempt is `Rejecting`: `stale`.
  3. Else the mode is `Inbox`: `received_by_node`.
  4. Else the boundary is not ready: ack `received_by_node` once with the journaled `receipt_op`, then retry on a later replay.
  5. Else: record the intent, then `inject`. `Handed` gives `handed_to_harness`; `Unknown` gives `delivery_unknown`.
- **Acks** reuse the journaled operation ID. Each ack is validated (`MessageNodeAck`), and so is its receipt (`MessageNodeAckReceipt`, which must echo the operation, delivery, attempt and disposition). If the ack response is lost, the retry sends the same operation and disposition.

### aq-agent (`crates/aq-agent-client/src/{mail,client,main}.rs`)

- **`message()` validation:** it now validates with `mail::valid`. A send to a `global_supervisor` recipient passes the local scope check, because the daemon authorizes that mailbox.
- **`message reply --message-id UUID [--task] [--body-file F] [--operation-id UUID] [--reply-id UUID]` (`AgentClient::reply`).**
  1. The body must be 1–16,384 UTF-8 bytes; it comes from the file or from bounded stdin.
  2. The client scans the bound inbox for the original message, reading up to 64 pages of 32. If the listing omits the entry's body, it re-reads that entry with `after = cursor-1, limit 1` to recover the sender.
  3. It sends a `MessageSend` on the original `thread_id` to `mail::reply_recipient(sender)`:
     - a session sender gets a reply in that session's mailbox;
     - a central supervisor sender gets a reply in `global_supervisor` for its `conversation_id`.

  When `--operation-id` or `--reply-id` is not given, it defaults to a fresh v4 UUID. Passing the same IDs makes a retry idempotent.
- **`message body --message-id UUID [--task]` (`AgentClient::body`).** It follows `next_offset` until `complete`, for at most 64 chunks and 16,384 bytes in total. Every chunk must keep the same `payload_digest` and cursor, and the offset must advance. It returns `{message_id, cursor, payload_digest, body}`. `--request-file` keeps the single-chunk form.

## Limits

- **Server and contract.** The server must accept the `global_supervisor` recipient from agent sessions and publish the supervisor shapes in aq-agent-api. This is a CROSS-REPO FOLLOW-UP (aq-server). Drop `aq_agent_client::mail`'s pin when the contract is re-vendored.
- **Not wired into launch.** `MailLoop` is a library API with tests. Two things are still to do:
  - driving it from the production `sandbox-run` loop at the renewal cadence;
  - feeding `AttemptInput` from the attempt's stop/suspend state.

  This is the same B2 launch-wiring blocker recorded in B7. No harness adapter implements `SafeBoundary` yet; H3 provides the qualified adapter guard.
- **No owner replies.** Agent-access v1 has no owner mailbox, so replies to owner senders are refused.
- **Bounded lookup.** `message reply` finds the original message only within the first 64 inbox pages of the bound mailbox.
- **Out of scope, per task:** F1b, F5, H3 policy, F4, H4, H1 and H7.
