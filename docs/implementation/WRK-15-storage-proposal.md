# WRK-15 storage follow-up proposal

Recommend a separately qualified redb prototype before runtime integration, with explicit approval before adding the dependency. Keep the reviewed JSON spool as the migration input/reference implementation. Do not build a custom transaction-log engine unless the prototype fails the footprint or latency gates below. No dependency or production storage change accompanies this proposal.

The measured problem is retained-history amplification: at12,740,029 bytes, prepare/send/ACK commit work took231/134/128 ms in one local release run. These operations change a small pending intent, retry timestamp or acknowledged prefix, yet clone/hash/serialize/fsync the whole journal. Idle polling is now independent of unrelated history, but collection still clones the active normalizer per record and rewrites global history once per batch. Changing storage alone does not eliminate the active-normalizer cost. The [qualified checkpoint](WRK-15-component.md) remains a pure component, not scalable runtime delivery evidence.

## Official source review

Research is pinned to redb4.4.0, official tag commit `7061f7e60d4573311c0636e161d417b93e9fd2b1`; this is a candidate version, not a dependency already accepted or tested here. The published release includes fixes for cache growth, compaction and integrity handling; a storage upgrade must therefore have regression qualification rather than relying on API names. [Official release](https://github.com/cberner/redb/releases/tag/v4.4.0).

The manifest specifies Rust1.90, edition2024 and MIT OR Apache-2.0; default std support and the existing libc dependency suffice for Linux without optional logging/chrono/uuid or experimental features. Our observed rustc1.96 meets that minimum. This checks manifest compatibility, not compilation or supply-chain approval. [Pinned manifest](https://github.com/cberner/redb/blob/7061f7e60d4573311c0636e161d417b93e9fd2b1/Cargo.toml).

The upstream design uses copy-on-write B+trees with one writer and MVCC readers. Durable commits support one-phase checksum recovery or two-phase fsync ordering; non-durable commits can be lost. Old readers and savepoints delay page reclamation. This supports row-level updates, but does not prove our workload latency, disk bounds or corrupt-input handling. [Pinned design](https://github.com/cberner/redb/blob/7061f7e60d4573311c0636e161d417b93e9fd2b1/docs/design.md).

WriteTransaction exposes Immediate durability, two-phase commit and quick-repair. Quick-repair persists allocator state, trading commit work for shorter crash recovery. Propose Immediate plus two-phase on every transaction; benchmark quick-repair on/off rather than silently taking a restart-cost tradeoff. No savepoints or non-durable mode are needed. [Official transaction API](https://docs.rs/redb/latest/redb/struct.WriteTransaction.html).

The stable StorageBackend interface includes offset reads/writes, length changes, sync and locking, allowing a capped private fd backend and deterministic fault counters. Builder also accepts an already opened File. Compaction requires transaction quiescence; it must be scheduled as explicit maintenance. These are mechanisms to qualify, not permission to trust arbitrary paths or suppress IO errors. [StorageBackend](https://docs.rs/redb/latest/redb/trait.StorageBackend.html), [Database](https://docs.rs/redb/latest/redb/struct.Database.html).

An independent append-log option must frame and checksum transactions; LevelDB's official record-format document illustrates why physical record framing/fragmentation is part of a real log protocol, beyond appending JSON. This proposal does not import LevelDB code or its recovery rules. File durability and directory-entry durability are separate: checkpoint publication must fsync the containing directory as well as file contents. [LevelDB log format](https://github.com/google/leveldb/blob/main/doc/log_format.md), [Linux fsync manual](https://man7.org/linux/man-pages/man2/fsync.2.html).

## Options and decision

| Concern | Bounded transaction log + checkpoint | Pinned redb prototype |
| --- | --- | --- |
| Small commit | Append a bounded canonical delta and fsync | Update changed rows/pages and commit |
| Implementation ownership | Transaction framing, torn-tail handling, replay, checkpoint selector, compaction and repair are ours | Upstream transaction engine; our schema, bounds, IO/private-file adapter and migration remain ours |
| Recovery bound | Replay at most configured segment bytes/transactions; checkpoint publication must select one exact generation | Open/recovery measured with quick-repair policy; corruption still refuses application admission |
| Disk budget | Straightforward fixed segment/checkpoint quotas, but old+new checkpoint+logs coexist during compaction | Logical quotas plus physical high-water/capped backend; COW space and maintenance headroom must be measured |
| Read model | In-memory full projection or custom index; startup replay cost | Indexed scoped rows with short read transactions |
| Main risk | Owning another storage engine before transcript runtime is qualified | New dependency and page-allocation/recovery behavior need workload-specific evidence |

Choose the redb prototype because delivery intents, exact immutable packet bytes, per-source known identities and acknowledged-prefix deletion fit transactional indexed rows. A bespoke log is viable at this size but adds a new crash/compaction protocol alongside worker authority and accounting protocols. This is an engineering recommendation, not a benchmark result: redb has not been added, compiled or performance-tested in this worktree.

If dependency introduction is declined, the concrete fallback is: one append-only active segment (at most8 MiB or1024 transactions), immutable checkpoint (at most16 MiB), at most one previous checkpoint and one replacement candidate, maximum64 MiB reserved disk. Every transaction has format, monotonic transaction ID, previous-commit digest, exact payload length, bounded typed delta and SHA256. Only a complete verified commit frame advances projection; incomplete final bytes hold recovery for explicit owned-tail resolution, while interior corruption refuses. An atomically published checksummed selector names exact checkpoint/segment generations; checkpoint fsync precedes selector rename+directory fsync, and pruning follows durable selector publication. No stale checkpoint/segment can reset node sequence. This avoids runtime global rewrites, but checkpoint creation remains O(history) and must run off the control lane. The same delta schema and acceptance suite apply.

## Concrete candidate schema and transaction boundaries

Use one private node spool database owned by one writer actor. Existing node owner.lock and canonical/private directory admission remain; create/open the database through an admitted no-follow fd or a tested equivalent capped backend, never a caller URL/path. Exact redb version and registry checksum must be recorded before adoption. No experimental multiprocess features, no background provider/network work, no persistent savepoints, no transactions held across HTTP or filesystem transcript reads.

Store versioned bounded values with canonical payload digests, not one serialized State row:

- `meta`: schema version, node/active boot/transport owner, next global sequence, ACK watermark, ordinary/gap counts and bytes, physical policy and migration receipt.
- `sources[source_id]`: immutable binding/native key/generation/parser plus small cursor/context metadata. Boot history and immutable replay intents have separate bounded keys.
- `seen[(source_id,native_key)]`: known normalized digest/EventRef/bounded raw fingerprints. Gemini message metadata and mutation provenance are separate bounded rows rather than hidden inside every source update.
- `outbox[sequence]`: exact immutable ObservationRecord bytes and digest, with event-ID uniqueness index. Source/binding validation and global sequence remain identical to CON03.
- `delivery`: at most one exact packet bytes/digest/message ID, prefix boundaries, attempt count/time/backoff; last exact receipt is separate. No network request is sent before durable packet commit.

Collection reads bounded admitted raw input outside storage transactions. A normalization delta names expected source cursor/context revision, changed known-identity rows, new facts and counters. The writer transaction verifies expected source/boot/parser state and quotas, inserts facts and changed identity rows, advances cursor/global sequence and commits together. Hold applies no delta; GapAndHold applies only the explicit loss interval/fence and reserved gap. No new fact can exist without its cursor/parser-state transaction. The normalizer API must evolve from full-source clone/apply toward a scoped read view plus bounded delta; a first row-store prototype may retain a bounded active-source clone for comparison, but may not claim that cost is solved.

Prepare reads at most32 contiguous same-boot facts/256 KiB and durably stores their exact Packet once. Begin-send updates only retry metadata. ACK validates against that exact packet, deletes only its prefix, adjusts durable quota counters and retains the exact receipt atomically. A duplicate receipt returns the retained result. Unknown commit/IO returns no new delivery authorization; reopen and resolve the retained intent before another network effect.

Use the existing logical limits unchanged initially. Add separately configured physical disk and cache bounds; a tentative128 MiB database cap with an8 MiB cache is a prototype budget, not a proven production bound. Soft ordinary admission must stop before the hard cap, leaving measured worst-case COW/transaction/gap/ACK headroom. A capped backend rejects out-of-budget growth before mutation extends the file; failure poisons the writer and triggers reopen, never cursor advance or inferred success. Proving reserved logical gap space does not prove physical allocation availability: disk-full can still force a conservative source hold. Actual data+maintenance+legacy-import bytes must fit the node reservation. Do not compact opportunistically during stop/renewal handling.

## Migration, recovery and compaction tests

Migration is explicit and offline under the existing owner lock. Validate the complete v1 JSON envelope/bounds/identity before creating anything; orphan pending.tmp or unknown members retain the current refusal. Hash and retain the original journal, import exact source/fact/pending/receipt identities into a new private candidate DB, verify projected counts/digests, commit+sync it, then publish a versioned selector and fsync the directory. Crash before publication leaves v1 authoritative; crash after publication resumes the exact DB. Never silently create an empty DB when an admitted store is missing/corrupt. A retained legacy backup is accounted in disk bounds and pruned only under explicit retention proof, never because import appeared successful. Downgrade to v1 is refused after any v2 write.

Required tests before choosing/adopting the implementation:

1. Run the existing35 pure tests against a storage abstraction/reference projection, including per-record quota rollback, reserved gaps, verified replay, boot transitions and exact packet/ACK replay. Add changed-ID payload/duplicate EventRef/sequence uniqueness and stored-count tamper checks.
2. Spawn child processes and kill at each observed backend write/sync and commit publication boundary, including collect, prepare, begin-send, ACK, boot, reparse begin/progress/finish and migration. Reopen must expose one whole committed projection, never cursor-only facts or ACK-only deletion. Distinguish process-crash tests from simulated torn writes and actual power-loss guarantees.
3. A deterministic backend simulates short writes, IO errors, ENOSPC, failed sync, truncated files and changed bytes. Exercise both commit slots/recovery, malformed values, bounds and exact old/new projection after every cut. Unrecoverable data refuses admission with bytes retained; a repaired store still undergoes application invariants before use.
4. Repeated collect/send/ACK cycles at small/large retained-history sizes; long readers intentionally held then released; verify bounded cache, physical growth, COW headroom and quota-counter equality to audited rows. Reclaiming acknowledged data never deletes parser dedupe history or unresolved intents.
5. Explicit compaction with no live transactions/network effects: child exits at each backend boundary; stable identity/cursors/facts/pending bytes before/after; refused compaction with active transactions; disk-cap exhaustion; recovery and continued writes. Compaction is maintenance, not a hidden admission dependency.
6. Every migration publication/rename/directory-sync boundary, duplicate migration intent, changed old bytes, orphan temp, missing/corrupt selected store, full disk, source old-boot provenance and pending unknown delivery. Compare v1/reference and v2 exact wire bytes; no namespace reset or history recharge.
7. Release benchmarks retain bytes read/written, sync counts, allocation/peak RSS, DB file/cache size, and p50/p95/max operation latency for idle/partial,32 tiny records, near64 KiB records, mixed sources, many Seen/native-message rows, repeated preparation/send/ACK and reopen after kill. Keep at least30 measured repetitions and compare quick-repair on/off. A fake coordinator loss/restart soak proves retained packet identity. Separate worker runtime tests prove actual stop/renewal responsiveness while IO/compaction blocks.

Review gates are dependency approval, exact-source standalone/crash qualification, real physical quota/headroom results and measured improvement across retained-history sizes. A provisional target is at least5× lower prepare/send/ACK CPU+bytes at the12 MiB snapshot, without an O(unrelated source history) slope; wall-clock/fsync tail latency is reported rather than promised. If redb misses those gates, keep the reviewed v1 implementation and evaluate the bounded-log fallback. No production migration, deletion or runtime completion is authorized by this document.
