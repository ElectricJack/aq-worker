Spec: aq-server `docs/specs/0006-agent-channel.md` §9 steps 2–5 and §10 phase 7 ("boat runner proxy reusing phase-3 code"; acceptance "No supported template ships `aq-agent`"). Branches: aq-server `chan/p7-server`, aq-worker `chan/p7-worker`.

Phase 7 is **not complete**: by decision it stops before removal (step 5), and the boat channel is a design note with owner questions, not code. What is done, and what is left, is listed below.

## §9 step 2: every agent route has its registry command (aq-server)

## §9 step 4: `aq result submit`

### How `aq-agent result` works

`aq-agent result submit --request-file F` and `aq-agent result status` (`crates/aq-agent-client/src/completion.rs`) implement the local result channel, contract `aq-agent-result-local-1` (`crates/aq-agent-result-local`).

- The worker installs a private outbox and names it in `AQ_AGENT_RESULT_DIR`. The outbox is 0700 and owned by the agent's uid. It holds `binding.json`, `presence.json` (boot ID plus the original BOOTTIME deadlines) and `owner.lock`, which the worker holds. Only `submissions/` is writable.
- `submit` adds the binding to `{"schema_version":1,"conclusion":…}` and publishes `submissions/submission.json` with create-only semantics (`RENAME_NOREPLACE`). It then waits at most 2 s, capped by the deadline, for a matching `ack.json`.
- There is no network and no credential. The codex native runner points `AQ_AGENT_RESULT_COMMAND` at the host's `aq-agent`. The docker-local Claude runner submits the final message itself through the same library (`sandbox_driver::submit_claim`).
- Before this phase, the bundle's `aq-agent` wrapper (#45) execed an `aq` that had no `result` command, so `/opt/aq/bin/aq-agent result …` inside a template exited 2.

### Design

- **Where the code lives.** The client is a port into aq-server `crates/aqv2/src/result.rs` (about 510 lines). It ports `completion.rs` and the `PrivateDir` parts of `files.rs` it uses: `openat`, `O_NOFOLLOW`, owner/0700 checks, `RENAME_NOREPLACE`, `flock`.
  - It runs on the contract crate vendored unchanged at `aq-server/vendor/aq-agent-result-local-0.1.0`. `source.json` there records aq-worker commit `56bf1fba`, the file digests and `Cargo.toml.upstream`; only the manifest is rewritten, to standalone dependencies. The wire types, canonical encoding and digests are therefore the worker's own.
  - A shared crate was not possible under the merge order (aq-server first): aqv2 cannot depend on an aq-worker crate that has not merged.
- **No secrets.** `result` opens no connection, never reads `AQ_CHANNEL`, takes no credential and never prints a path or a raw error. An unusable channel or request prints the fixed `invalid_contract_or_private_state` document on stderr with exit 15, as `aq-agent` did.
- **CLI.** `aq result submit --request-file F` and `aq result status`. Any other `result …` tokens (`result show`, `result list`, … in `commands.json`) still go to their registry commands.
- **Output.**
  - Human mode prints the same compact document on stdout, with `aq-agent`'s exit statuses: 0 ready or recorded, 10 pending, 11 conflict, 13 reconcile or unknown, 15 refused.
  - `--json` wraps the document in `{"schema_version":1,"data"|"error":…}`.
- **Wrapper.** `/opt/aq/bin/aq-agent` stays `exec /opt/aq/bin/aq "$@"`. `aq-agent result submit|status` therefore becomes `aq result submit|status` with no rewriting. The bundle build now checks this: `aq-agent result status` without a channel must print `invalid_contract_or_private_state` (`Dockerfile.runtime`, asserted by `tests/runtime_bundle.rs`).

### Golden test (both repos)

- **aq-server.** `crates/aqv2/tests/golden/result.json` is generated by `tests/cli/result.rs` in the existing `cli` binary. It runs the real binary on a fixture outbox through these steps:
  1. ready;
  2. new claim, pending after the bounded wait;
  3. the same claim (replay);
  4. a changed claim (11; the original is kept);
  5. the worker's `accepted` and `recorded` acknowledgments;
  6. `--json`;
  7. no channel (15).

  It pins each step's exit status, stdout and stderr, plus the published `submission.json` bytes. A second test refuses a symlinked request, an oversize request, a request with privileged fields, and a group-accessible root.
- **aq-worker.** `crates/aq-agent-client/tests/fixtures/result-golden.json` is the same file, copied verbatim. `tests/completion.rs::aq_agent_result_matches_the_aq_result_submit_golden` runs `aq-agent` on the same steps (7 shared steps; the two `--json` steps are aq-only) and compares byte for byte. Both pass, so the two clients print identical documents and write identical claims.

### Pin

`packaging/sandbox/pins.json` input `aqv2` moves to the aq-server commit that has `aq result`. Evidence is in [`0006-P7-evidence/`](0006-P7-evidence/).

- **Pin.** aq-server `85070006a0bec9298d18252ed98cc63afe36cc5e` (the merge commit of aq-server #111), SHA-256 `1111267136ac03c21728981ac60bf2424de4f7db420a34abcdd681150da924d6`, 5,679,368 bytes, `static-pie linked`. The previous pin was `e058e7d7`, `eef04c98…`.
- **Reproducible.** Two clean `build-aqv2.sh` builds at the merge commit gave this digest, and so did two earlier builds at #111's head `52e68a52`, which has the same source (`aqv2-builds.log`).

- **The static binary.** All 9 golden steps match when run against the static binary itself (`golden-static-musl.log`).
- **Real bundle build.** The runtime bundle was built from this branch with the pinned public inputs and the `aqv2` from #111's head (byte-identical to the pinned one) (image `sha256:8978e4bc…`) and passed every check, including the new `aq-agent result status` mapping (`bundle-checks.log`). The installed `/opt/aq/bin/aq` has the pinned digest (`bundle-manifest.json`). The previous pin's `aq` has no `result` command and would fail that check.

## Boat: design note and owner questions (not built)

§10 asks for "boat runner proxy reusing phase-3 code". It was not built, for two reasons.

### 1. There is no boat agent launch to attach a channel to

- The only path that runs a real agent in a sandbox is docker-local: `native/launch/claude_docker.rs` → `sandbox_driver::run`, which constructs `DockerLocalBackend` directly.
- `aq-worker run` with a `boat` backend builds a `Controller` with `UnavailableProvider` ("B2 registration/issuance provider is not installed"), so it never admits work.
- The boat VM runs only the template's fixed command or the operator's `runner_command`. C7 says this "does not qualify the production B6b launch path".
- No code issues, delivers or uses any AQ credential for a boat attempt, and nothing in a boat VM talks to aq-server today.
- `BoatBackend::create` refuses `agent_channel` because there is nothing behind it. That refusal is the correct fail-closed behaviour until a boat launch exists.

### 2. "Credential on the node" cannot hold for boat as placed

- The agent's container runs inside a remote boat.dev VM.
- The node reaches that VM only through Boat's HTTPS control API (`exec`, file upload and download; 4 MiB responses; 0.21–0.26 s RTT measured in C7).
- The VM firewall drops all inbound traffic except Boat control TCP 8911. The node is usually behind NAT. C7 forbids the SSH, port-publishing and hosting endpoints.
- So no socket can be shared between node and VM. A bind mount is physically impossible, and there is no forwarding primitive.

Spec §5.3 already says so: for remote backends the same forwarding code runs inside the sandbox, as the runner user, and holds the agent credential and the runner Access token. That moves the credential off the node, which the owner has not yet approved for boat.

### Options, once a boat launch exists

| | A. In-VM runner proxy (§5.3) | B. Node relay over the Boat API | C. Tunnel to the node |
| --- | --- | --- | --- |
| Credential | In the VM, in the runner process's memory (runner uid 10001), never readable by the agent uid 10002 (B6b privilege split) | Stays on the node | Stays on the node |
| Reuse of phase 3 | `AgentChannel` and `forward` from `aq-agent-channel` unchanged, plus a new `CredentialIssuer` that reads node-pushed credentials. `NodeIssuer` stays on the node and rotates; each new token is pushed in by Boat file upload into a runner-only 0700 path (as private material is today), read and unlinked. | The `forward` core on the node; an in-VM shim turns each socket request into an outbox file, and the node polls it with `exec`/file reads | `AgentChannel` on the node, unchanged |
| Upstream | VM → aq-server over the internet, so it needs the runner Access token in the VM | Node → aq-server, as today | Node → aq-server |
| Cost | New secret custody in the VM; push-based rotation | Two or more Boat API round trips per call (≥0.5 s), Boat API rate and quota, 4 MiB cap, no streaming | Node must expose a WireGuard or other endpoint; new network policy |
| Fail-closed | Launch checks `test -S /aq/channel/aq.sock` through `exec` before the harness starts; revocation closes the channel via `session_revoked` | Shim refuses when no node poll is live | Same as docker-local |

Recommendation: A, because it is the spec's own design and B would make every agent command slow and quota-bound. It needs explicit owner sign-off on the custody change.

### Questions for the owner

1. Is a boat agent launch (B2 provider, in-VM runner, Claude/Codex material, copy-back, transcript and leak guard) scheduled? The boat channel depends on it. It is much larger than phase 7.
2. For boat, do you accept §5.3 custody? The agent credential and a runner Access token would live in the VM's runner process, outside the agent uid, instead of "credential on the node". Or must boat use the node relay (B), with its latency and Boat API cost?
3. Under A, should the runner Access token be a separate, path-restricted Cloudflare Access service token per boat node, allowed only `/api/v1/commands*` and `/api/v1/operations/*`?

Until these are answered, boat keeps refusing `agent_channel`, and a boat attempt can never run an agent without a channel.

## §9 step 5: retirement (not done in this phase)

### Removal checklist

Removal is allowed only after the verification below shows no supported template still ships `aq-agent`.

**1. Template generation that drops the wrapper (aq-worker, first).**

- **Bundle build.** `packaging/sandbox/Dockerfile.runtime`: delete the `printf … > /opt/aq/bin/aq-agent`, `chmod 755 /opt/aq/bin/aq-agent`, the `aq-agent --help` check and the `aq-agent result status` check. Add `test ! -e /opt/aq/bin/aq-agent`.
- **Manifest.** `packaging/sandbox/bundle_manifest.py`: drop `agent_client_wrapper`.
- **Tests.** `crates/aq-worker/tests/runtime_bundle.rs`: drop the wrapper fixture (`bin/aq-agent`) and the wrapper asserts, and assert that the manifest has no `agent_client_wrapper`.
- **Docs.** `packaging/sandbox/README.md`: remove the wrapper from "Installed interface" and the deprecation note. `crates/aq-worker/src/sandbox_driver.rs` `RUNNER_NOTE` already names neither tool.
- **Publish.** Build and publish the new `aq-sandbox-runtime`, then rebuild every supported template from it (`aq-worker template build …`). Each new allowlist entry's `provenance.runtime_bundle_digest` is the new bundle digest. This is the template generation that drops the wrapper.
- **Host-side `aq-agent` users** (not templates, but they keep the binary alive):
  - `scripts/package-native-runtime.py` (`aq-agent` in the native runtime);
  - aq-server `scripts/ms1-profiled.py` (`pin("aq-agent", …)` for the `aq-agent-result-client-named-readonly-v1` profile);
  - aq-codex-mapper's `AQ_AGENT_RESULT_COMMAND` client path.

  Re-point them to the static `aqv2` (`… result submit`). These are pinned profile artifacts, so this is a new profile version with the new client digest.

**2. Verify that no supported template ships `aq-agent`.**

The supported templates are every entry in the vault template allowlist (`templates/allowlist.json`), plus every template digest in a node run config (`docker_local.templates`, `boat.templates`) and in every host profile's template pin. For each image digest D:

```sh
docker run --rm --network=none --entrypoint /bin/sh "IMAGE@D" -c \
  'test ! -e /opt/aq/bin/aq-agent && ! grep -q agent_client_wrapper /opt/aq/manifest.json && /opt/aq/bin/aq --version'
```

- Every digest must pass. A boat saved snapshot is checked through its allowlist entry, which names the same OCI digest. Equivalently, every allowlist entry's `runtime_bundle_digest` must be the wrapper-less bundle or a later one.
- Remove failing entries from the allowlist and from node configurations first (stop offering them), then run the check again.
- Also confirm on the server that no live attempt is still on an old template: none in `GraphActive`/`Running` was launched from a removed digest.

**3. aq-worker removal** (after step 2 passes):

- **The binary.** Delete `crates/aq-agent-client/src/main.rs` and the `[[bin]] aq-agent` target, `scripts/package-agent-client.py`, and the `aq-agent` entry in `scripts/package-native-runtime.py`.
- **The Graph and HTTP client modules**, `client.rs`, `comments.rs` and `context.rs`, with their tests: `tests/client.rs`, `tests/contract_artifact.rs`, and the `cli_*` tests in `tests/completion.rs`. Lower `build-budget.toml` test binaries with `--update`.
- **What stays.**
  - `completion.rs` (+`files.rs`) is used by the node runner's `sandbox_driver::submit_claim`. Keep it, or move it into a small `aq-agent-result-client` crate.
  - `mail.rs` is used by `native/runner/sandbox/mail.rs`.
  - `provision.rs` (the B7 fallback, `native/runner/sandbox/agent_access.rs`) stays until the remote-backend decision above. Drop it if boat chooses option A.
- **Golden copy.** Keep `tests/fixtures/result-golden.json` checked against `completion.rs`, or delete it with the binary if the runner moves to `aq result submit`.
- **Channel prefix.** `crates/aq-agent-channel/src/forward.rs` `AGENT_PREFIXES`: drop `/v1/agent/`, so the channel refuses it (`channel_refused`). Update `tests.rs`, which uses `/v1/agent/context` as a forwarded path.

**4. aq-server removal** (after the aq-worker channel no longer forwards `/v1/agent/`):

- **Keep the handlers.** The command surface forwards in process to each command's agent route through the listener's inner router (`commands.rs` `invoke` → `Surface.inner`). Removing the routes from the router alone would break every agent command.
  - Either mount the `/v1/agent/*` routes only on the internal router the command surface dispatches to (not on the machine listener),
  - or give each registry agent route an internal path and point `aq-command-registry` at it.
- **Then unmount from the machine listener:**
  - `/v1/agent/context` and `/v1/agent/graph/read` (`agent_access.rs`);
  - `/v1/agent/graph/commands` and `/v1/agent/operations/{id}` (`agent_access/mutations.rs`);
  - `/v1/agent/messages/*` (`agent_access/messaging.rs`);
  - `/v1/agent/questions*` (`agent_access/questions.rs`);
  - `/v1/agent/waits/*` (`agent_access/waits/routes.rs`);
  - `/v1/agent/tasks` (`agent_access/agent_tasks.rs`);
  - `/v1/agent/comments*` (`agent_access/human/comments.rs`, `aq-task-comments` `ROUTES`).
- **Delete `/v1/agent/context` and its handler.** `whoami` replaces it. Remove its `agent_legacy` row from `protocol/commands/v1/routes.json`, and the `AgentLegacy` class if nothing else uses it.
- **Keep:** the node recovery routes `/v2/worker/agent-operations/query` and `/retry`, `/v2/worker/agent-session` (issuance) and the `aqa_` credential.
- **Admission.** `admission.rs`: drop the `/v1/agent/` class branch.
- **Contracts.** Mark agent-access-1 superseded for the removed routes in `protocol/agent-access/v1/README.md` and `MANIFEST.json` `status`, keeping the node recovery routes. Mark `agent-comments`, `agent-questions` and `agent-waits` v1 superseded.
- **Tests.**
  - Replace direct `/v1/agent/*` calls with `/api/v1/commands/*`: `it_access` `agent_route_grants`, `agent_task_comments`, `agent_access`, `messaging`, `graph_mutations`, and `it_server` `commands::section_9_…` (make it assert that the routes are not mounted).
  - Add a test that the machine listener answers 404 for each removed path.
- **Spec.** Mark §9 step 5 done in the spec. The acceptance is "No supported template ships `aq-agent`" (step 2 above), with the step-2 evidence recorded.
