## Contract decisions

The delegated credential is an opaque server-verified secret associated with a
public permit ID and immutable claims. Pure validation never authenticates a
credential. The issuer must mint unpredictable credentials, retain or verify
claims, compare authenticated node/attempt/grant state, and enforce revocation.
Changing JSON claims cannot mint authority. Credentials must never be logged.

Both preparation and execution permits carry an attempt, allocated grant
generation, sandbox, node/boot, hard deadline and sandbox channel. Preparation
uses the reserved next grant generation (positive even before launch); it can
fetch preparation material and report preparation observations/artifacts but
cannot start, renew execution, publish a result, accept offers or register nodes.
Execution requires a current grant and never outlives its renewable or hard
expiry. Absolute times are server epoch milliseconds; expiry equality is expired.
B2 is responsible for authenticated current context and clocks.

A sandbox has one server-assigned channel ID, stable through re-adoption. Its
full binding includes node identity for per-node aggregates. Callers validate
against server-owned binding rather than trusting a caller-selected channel;
B2/B6c enforce allocation uniqueness and aggregate limits.

Re-adoption lists the prior and new boot and each sandbox/attempt/generation.
Every input receives a rebound permit or typed refusal. Rebinding preserves
permit ID, sandbox, attempt, generation, channel, scope and all original times;
the secret may rotate. Exact request/response replay is idempotent only within
the existing deadline. Changed requests or responses for the same operation ID
are conflicts. Persistent replay fencing and atomic server updates belong to B2.
The awaiting-node-re-adoption renewal variant carries no expiry or grant clock.

Registration v2 includes backend kind, bounded capabilities and templates,
positive concurrency limit, optional currency/micro-unit spend ceiling, exact
harness versions, and estimated cold-start latency and currency/micro-unit cost.
Unknown required capability strings return an explicit typed decline. Older
peers must negotiate before accepting; frozen registration decoding rejects the
new envelope rather than dropping fields. No silent fallback is authorized.

## Phase renewal gap and handoff

The B6a1 report on this task identified that `DurablePhaseExecution` cannot
produce legacy `Granted`, and server `initial_authority.rs` deliberately refuses
phase origins in its legacy-only loader. The new `sandbox/renewal.rs` projects
both phase-v2 and refresh execution receipts into `PhaseExecutionAuthority` and
checks delegated handoff against native grant identity and deadlines. This is
an explicit new renewal path, not a conversion to legacy authority.

`RunnerRenewalRequest` carries immutable original receipt/profile/grant identity,
the current permit and installed revision. `RunnerRenewalResponse` validates
operation correlation, current binding, live prior permit, increasing revision,
unchanged hard deadline, monotonic expiry, and physical delivery nonce. Its local
deadline helper caps replayed revisions and cannot revive expiry. Awaiting node
re-adoption has no clock. Original receipt identity keeps the old boot while
post-readoption permits match trusted current context. Stable grant generation
maps to native assignment generation; renewal revision is separate.

B2 authenticates credentials, verifies exact original receipt and revision,
atomically persists renewal/replay and fences current boot. B6 installs the
phase runtime adapter and durable launch handoff, retaining local deadlines and
stopping/preserving on renewal loss. Wire shape does not prove those effects.
