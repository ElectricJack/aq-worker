### New defects (rerun)

**R3. The project's admission-artifact quota stops all offers, silently.** Critical; **blocks acceptance** (§7.2 always-on; Steps 6, 7 and 8 here). Owner: server, sealed history (the S16 decision).
- `admission_artifact_insert_guard()` refuses at 512 rows per project (and 4096 in total).
- The aq-ms1 project reached 512 after 33 offered attempts in the stack's life. The rows break down as composition 180, startup 132, source retention 76, plus graph snapshots, outcomes, selections and catalogs. That is about 15 per attempt.
- Nothing has expired, and the rows are sealed history, so nothing can be pruned.
- From then on `artifacts::retain` fails (`crates/aq-server/src/profiled_execution/artifacts.rs:264`, the INSERT; Postgres: `ERROR: admission artifact quota`). The poll answers 409 `inline artifact owner unavailable or inconsistent` on every slot.
- `/api/v1/swarm` shows the machine `online` with no waiting reason.
- The S16 analysis did not list this cap. It expected the first stop after about 256 attempts per node or project; this one comes after about 33 per project.
- Repro: any project once its `admission_artifacts` count reaches 512; then poll.
- Evidence: `defects/r3-artifact-quota/`.

**R1. A preparation failure leaves the slot in a recovery loop it never leaves.** Important; **blocks acceptance** (§7.2 restart recovery: one transient error permanently loses a slot). Owner: W4/W7 (recovery of a pre-Running attempt), and the worker's native HTTP client.
- After the 3b crash, slot 2's retry `1d9d4a23` got `503 {"error":"overloaded","message":"request capacity exhausted; retry the same operation"}` from `/v1/worker/profiled/artifact`. The worker does not retry the same operation; it fails the attempt.
- The attempt stays in `current`. Recovery then fails on every retry, before and after a service restart, with "missing or mixed exact phase execution" (`crates/aq-worker/src/native/journal/phase_view.rs:60/80`, reached from slot recovery). The backoff runs 30 s → 300 s.
- The server released the attempt and re-offered the task elsewhere, so only the slot is lost.
- Repro: any failure between offer acceptance and phase execution (for example a 503 on an artifact download), then wait for the slot's recovery.
- Evidence: `defects/r1-prep-failure-recovery/journal.txt`.

**Minor.** Two minor items:
- The dashboard's Swarm read occasionally answers 503, and terminal reads answer 500, under load (D12 class).
- The service's first poll after a restart can race the server's per-node request capacity (`503 overloaded`), which feeds R1.

### Defects

Severity: critical (the feature cannot work), important (a spec or owner answer is broken in a common case), minor.

**D1. The service's default state layout is too long for the session host's sockets.** Critical, **blocks**. Owner: W6 `Layout` (and the aq-session-host guard).
- With `Layout::for_profile`, the host root is `~/.local/state/agent-q/service/<profile>/slots/<n>/current/host`, which is 65 bytes for `/home/jkern`.
- The session host puts `tmux.sock`, `observed-gate.sock` and `terminal-{reader,viewer}.sock` in `<root>/<launch uuid>/`.
- With the default root, the session host refuses: "native host bootstrap refused: tmux socket path too long" (112 bytes; its own check is `< 104`).
- With `XDG_STATE_HOME=~/.s` the root is 55 bytes, `tmux.sock` passes at 102, but the 18- and 20-byte names reach 111–113 and the guardian dies: "guardian exited before identity".
- The root must be about 50 bytes or less. No XDG location under a normal home gets there, because the fixed tail is 41 bytes.
- Repro: run the documented install on any `/home/<user>`, then offer it a task.
- Workaround used: `state_root = "/home/jkern/.aq"` in `service.toml` (backed up as `service.toml.bak-pre-state-root`).

**D2. Slot recovery can never succeed.** Critical, **blocks** §7.2 restart recovery. Owner: W6 `AqGit`, W7 `Supervisor::recover`.
- (a) `recover` restarts aq-git on the slot's existing state, then always sends `repo.register` with `expected_binding_generation: 0`. aq-git answers `binding_conflict` "Repository already registered". The slot retries recovery with backoff (to 300 s) forever.
- (b) After SIGKILL, the killed aq-git leaves `current/git.sock` behind. `AqGit::start` waits only for the path to exist, so it returns at once while the new aq-git cannot bind, giving "connect to aq-git: Connection refused".
- The unit tests use a fake git.
- Consequences:
  - an attempt that fails before Running, or one interrupted by a crash, is never reported or salvaged;
  - its slot is lost;
  - its task stays held (`replacement_prior_execution_uncertain`): tasks 7a1–7a4 and 7a9.
- Changing `state_root` (or the renderer) then makes the node's re-registration fail with "prior execution claims remain held". Revoking the machine does not release those claims.
- Repro (a): any attempt that ends without a report (for example D1 or D3), then wait for the slot's retry.
- Repro (b): `systemctl --user kill -s KILL aq-node@P` while an attempt runs.

**D3. At startup, slots poll before the renderer pin arrives.** Important, **blocks** adding a machine while a renewal exists. Owner: W7 (startup) / W9.
- A fresh state root has no `renderer.json`, so the slots use the template renderer. The first `/v1/worker/control` answer, which carries the current renewal, comes only after the first poll.
- The server offers with its current renewal (`8bcf3577…`). The node accepts the offer, then refuses it: "unsupported startup renderer qualification". The attempt is retained, and D2 wedges the slot.
- This is Review Focus 4 at service start.
- Repro: purge and re-enroll a machine (or enroll a second machine) while a renewal is effective.
- Workaround used: availability off until the new pin was effective and persisted.

**D4. Handoff notices for slots 2 and up are refused.** Important, **blocks** Q1 and §7.2 on a multi-slot machine. Owner: W9 `run_service` (slot 1's `ServerLink` is the only `ControlSource`), or S4 `record_handoff` (`attempt_not_owned` checks only the posting node).
- On a graceful stop, slot 2's `service_stop` notice gets 400. So the handoff is not recorded, it is charged to the budgets, and the successor reuses the predecessor's export: the saved work is discarded.
- Repro: `systemctl --user restart aq-node@P` while slot 2 runs an attempt.
- Dashboard Stop is not affected: the server writes those rows itself.

**D5. A handoff successor is refused on every poll, and the refusal fails the whole poll.** Critical, **blocks** §7.2 Stop/Start, Q1, Steps 5, 6 and 9. Owner: S7 (successor export), S9 (backstop).

  - the retention handle is the candidate operation, which is neither the configured base handle nor the D1 publication head handle;
  - the observation's selection is `Immutable{candidate}`, while the configured source is `NamedRef refs/heads/main`.
- `unavailable()` is an unlogged `AppError::Conflict`, so the poll answers 409. That is not one of the refusals S9 skips, so the same task is chosen again on every poll from every slot.
- The machine takes no other work (tasks 7a7 and 7a8 starved) until the task is retired.
- The reasoning is from reading the code: no successor export row exists, and no `aq_refusal` or Postgres error was logged at any refused poll.
- Repro: Stop worker with a running agent, then Start worker. Or restart the service while slot 1 runs.
